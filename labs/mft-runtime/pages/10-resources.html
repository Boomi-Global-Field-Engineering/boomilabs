The mental model behind everything you just did, plus reference material.

Concepts recap

An Organization is the top-level container holding your Endpoints (the sources/targets, like your File Share). Your Runtime is assigned to those endpoints to physically pick up or deliver files. The runtime always initiates the connection outward as a client — it never accepts inbound connections, which is why only one outbound port (443) is ever required.

Cloud ↔ Runtime (inbound/outbound)

The most common pattern. A file is staged in the MFT cloud and the runtime pulls it down, or the runtime picks up a local file and pushes it to the cloud for a partner to collect. The cloud is the intermediary.

LAN to LAN

The runtime moves a file from one local location to another entirely within your network, without the file ever touching the MFT cloud. Useful for sensitive files or when egress cost is a concern. This is the pattern you just built.

Direct delivery / fan-out

The runtime picks up one source file and delivers it simultaneously to multiple external destinations, each with its own independent processing — common in manufacturing, retail, and supply chain scenarios.

Frequently asked questions

Why does the runtime copy files instead of moving them?
During a transfer the runtime may need to process the file (encrypt, compression). It keeps the original in place until processing completes, so if something goes wrong your original file is still safe.
What is the heartbeat, and why does it matter?
It's a recurring API call the runtime sends to the cloud every few minutes to say "I'm still here." If no heartbeat arrives within 5 minutes, an alert fires. A green heartbeat is your confirmation the install succeeded.
Can two runtimes talk directly to each other?
No. Runtimes never connect to each other directly — every transfer between two runtimes goes through the MFT cloud. The runtime always initiates the connection outward; it's a client, never a server.
What ports does the runtime need?
By default just one: 443 outbound. But if you need the runtime to talk directly to other external SFTP, FTPS, or even FTP servers, you may need to open other ports that those servers require. No inbound firewall rules are ever required, because the runtime always initiates the connection to the cloud.

Appendix: Pre-installation checklist

For reference — this is what a customer environment needs before a real (non-workshop) install. Most of this is already handled for you on the workshop VM.

System & access

  • OS version confirmed and supported
  • PowerShell 5.1 or later confirmed (Windows only)
  • Admin user account identified
  • Permission to create a Scheduled Task confirmed (Windows only)

Network

  • Port 443 outbound confirmed open with network/firewall team
  • Proxy settings documented, if applicable

Linux configuration

  • SystemD or CronTab decided (SystemD recommended — Linux only)

Storage planning

  • Installation drive and path decided
  • Temp repository drive and path decided (separate drive recommended)
  • Log folder location decided
  • Available disk space calculated (at least 2x peak transfer load)
  • Flow endpoint volume estimated, if high volume
Tip
Store your temp repository on a separate physical drive from your installation directory in production. This prevents storage contention during high-volume transfers.
