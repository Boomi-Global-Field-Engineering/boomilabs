Build a Simple API

In this exercise, you will create an API microservice abstracting the more complex Salesforce API. You will use the top down API design pattern to create this API by first creating the API specification and then automatically generating the Boomi Process stub that conforms to the API contract. Then you will complete the implementation of the service to search for customers in Salesforce. These lower level system specific APIs are commonly used in more higher level Business or Composite APIs that we will see in the next exercise. We will introduce you to the Boomi API Management perspective and have you interact with the Boomi API Service Catalog to discover and test out the API using the Swagger Visualization Portal.

Step 2 of 2

Build a Complex API

In this exercise, we will have you implement a complex composite API that calls 2 microservice APIs. One microservice API will get Salesforce account data and the other API will get the SAP Sales Orders. The composite API will get the entire customer profile information that can be used by both internal and external API consumers. We will use the Boomi API Management perspective to discover APIs and test them out. While it is out of scope for this workshop, Boomi does provide an API Gateway and API Developer Portal the facilitate inbound access to API’s from the internet or from your intranet. Runtime Plans can be created to limit the specific API Consumer/API Provider pair to only allowing so many calls per time period (Rate Limit) and so many calls over a time span (Quota Limit). The API request message size can also have an upper limit. Boomi supports advanced security options to secure your APIs with no authentication, basic auth, client certificate auth, SAML, OAuth2 with or without JWT tokens. Boomi can connect with external identity providers for enterprise authentication and secure the APIs from the Boomi runtime or API Gateway.
